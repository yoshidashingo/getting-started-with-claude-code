## 要件定義とは

`requirements.md`は、**何を作るべきか**を定義するドキュメントです。プロダクトの機能要件をUser Story形式で記述し、開発チーム全体で共有可能な明確な仕様を提供します。

### requirements.mdの役割

```text
要件定義の目的:
✓ ユーザー視点での機能記述
✓ 開発すべき内容の明確化
✓ 受け入れ基準の設定
✓ 優先順位の明確化
✓ トレーサビリティの確保
```

### 基本構造

```markdown
# Requirements Specification

## Overview
プロジェクトの概要

## User Stories
### US-001: [機能名]
- As a [ユーザータイプ]
- I want to [やりたいこと]
- So that [得られる価値]

#### Acceptance Criteria
- [ ] 受け入れ基準1
- [ ] 受け入れ基準2

#### Priority
[High/Medium/Low]

#### Status
[Draft/Approved/In Progress/Done]
```

## User Story形式の書き方

### 基本フォーマット

User Storyは**3つの要素**で構成されます：

```markdown
As a [役割]
I want to [行動]
So that [理由/価値]
```

### 良いUser Storyの例

#### 例1: ユーザー登録機能

```markdown
## US-001: ユーザー登録機能

### User Story
As a 新規ユーザー
I want to メールアドレスとパスワードで登録できる
So that アプリケーションのサービスを利用できる

### Description
新規ユーザーがアプリケーションにアカウントを作成できる機能。
メールアドレスの検証とパスワードの強度チェックを含む。

### Acceptance Criteria
- [ ] ユーザーは有効なメールアドレスを入力できる
- [ ] パスワードは8文字以上で、大文字、小文字、数字を含む必要がある
- [ ] 既に登録済みのメールアドレスの場合、エラーメッセージが表示される
- [ ] 登録成功後、確認メールが送信される
- [ ] 確認メール内のリンクをクリックするとアカウントが有効化される

### Priority
High

### Status
Approved

### Dependencies
- None

### Related
- Design: [design.md#authentication-system](../design.md#authentication-system)
- Tasks: [tasks.md#user-registration](../tasks.md#user-registration)
```

#### 例2: 検索機能

```markdown
## US-002: ユーザー検索機能

### User Story
As a 管理者
I want to 名前やメールアドレスでユーザーを検索できる
So that 特定のユーザーを素早く見つけて管理できる

### Description
管理者がユーザーリストから特定のユーザーを検索する機能。
リアルタイムでの絞り込みと複数条件での検索をサポート。

### Acceptance Criteria
- [ ] 検索バーに入力した文字列でリアルタイムに絞り込める
- [ ] 名前、メールアドレス、ユーザーIDで検索できる
- [ ] 検索結果は0.5秒以内に表示される
- [ ] 検索結果が0件の場合、適切なメッセージが表示される
- [ ] 検索履歴が保存され、再利用できる
- [ ] 検索条件をクリアできるボタンがある

### Priority
Medium

### Status
In Progress

### Dependencies
- US-001 (ユーザーデータが存在する必要がある)

### Technical Notes
- インデックス作成による検索パフォーマンス最適化が必要
- 1000件以上のユーザーでもスムーズに動作すること
```

### User Story作成のガイドライン

#### 1. INVEST原則

良いUser Storyは**INVEST**原則に従います：

| 原則 | 意味 | 具体例 |
|------|------|--------|
| **I**ndependent | 独立している | 他のStoryに依存せず実装可能 |
| **N**egotiable | 交渉可能 | 実装方法は柔軟に決定できる |
| **V**aluable | 価値がある | ユーザーに明確な価値を提供 |
| **E**stimable | 見積もり可能 | 実装工数を見積もれる |
| **S**mall | 小さい | 1-2週間で完了できる |
| **T**estable | テスト可能 | 明確な合格基準がある |

#### 2. ユーザー役割の明確化

```markdown
# 良い例：具体的な役割
As a 管理者
As a 一般ユーザー
As a ゲストユーザー

# 悪い例：曖昧な役割
As a ユーザー  # どのタイプのユーザー?
As a 人  # 役割が不明確
```

#### 3. 行動の明確性

```markdown
# 良い例：具体的な行動
I want to メールアドレスとパスワードでログインできる
I want to プロフィール画像をアップロードして変更できる

# 悪い例：曖昧な行動
I want to システムを使える  # 何をする?
I want to データを見る  # どのデータ?どう見る?
```

#### 4. 価値の明確化

```markdown
# 良い例：具体的な価値
So that セキュアにアプリケーションにアクセスできる
So that 自分のアカウントを他のユーザーと区別できる

# 悪い例：曖昧な価値
So that 便利になる  # どう便利?
So that 良くなる  # 何が良くなる?
```

## Acceptance Criteriaの定義

Acceptance Criteria（受け入れ基準）は、User Storyが完了したと判断するための**具体的な条件**です。

### 効果的な受け入れ基準の書き方

#### 1. Given-When-Then形式

```markdown
## US-003: ログイン機能

### Acceptance Criteria

#### AC-1: 正常なログイン
Given ユーザーが有効なアカウントを持っている
When 正しいメールアドレスとパスワードを入力する
Then ダッシュボードにリダイレクトされる
And セッションが作成される

#### AC-2: 無効な認証情報
Given ユーザーがログインページにいる
When 誤ったパスワードを入力する
Then "メールアドレスまたはパスワードが正しくありません"というエラーが表示される
And ログインフォームはクリアされない（メールアドレスは保持）

#### AC-3: アカウントロック
Given ユーザーが5回連続でログインに失敗した
When 6回目のログインを試みる
Then "アカウントがロックされました。15分後に再試行してください"というメッセージが表示される
And ログインフォームが無効化される
```

#### 2. チェックリスト形式

```markdown
## US-004: ファイルアップロード機能

### Acceptance Criteria
- [ ] ユーザーはドラッグ&ドロップでファイルをアップロードできる
- [ ] サポートされるファイル形式: JPG, PNG, PDF (最大5MB)
- [ ] アップロード中は進捗バーが表示される
- [ ] アップロード完了後、サムネイルが表示される
- [ ] 複数ファイルの同時アップロードに対応（最大10ファイル）
- [ ] ファイルサイズ超過時は適切なエラーメッセージが表示される
- [ ] 非サポート形式の場合もエラーメッセージが表示される
- [ ] アップロードはキャンセル可能
```

#### 3. 数値基準を含める

```markdown
## US-005: ダッシュボード表示

### Acceptance Criteria

#### パフォーマンス要件
- [ ] ページの初期表示は2秒以内に完了する
- [ ] 1000件のデータでもスムーズにスクロールできる
- [ ] チャートのレンダリングは1秒以内に完了する

#### 機能要件
- [ ] 直近30日分のデータが表示される
- [ ] データは5分ごとに自動更新される
- [ ] 最低3種類のグラフ（棒グラフ、円グラフ、折れ線グラフ）を表示

#### アクセシビリティ要件
- [ ] WCAG 2.1 AA基準に準拠
- [ ] キーボードのみで全機能が操作可能
- [ ] スクリーンリーダーで適切に読み上げられる
```

### 受け入れ基準のベストプラクティス

⚠️ **重要な原則:**

1. **測定可能**: 主観的でなく客観的に判定できる
2. **具体的**: 曖昧さがなく明確
3. **完全**: すべての重要な条件をカバー
4. **テスト可能**: 自動/手動テストで検証可能

```markdown
# 良い例
- [ ] パスワードは8文字以上、大文字・小文字・数字を各1文字以上含む
- [ ] エラーメッセージは画面上部に赤背景で3秒間表示される
- [ ] 検索結果は500ms以内に表示される

# 悪い例
- [ ] パスワードは十分に強固である  # 何をもって"十分"?
- [ ] エラーがわかりやすく表示される  # "わかりやすい"は主観的
- [ ] 検索が速い  # "速い"の定義は?
```

## 良い要件と悪い要件

### 良い要件の例

```markdown
## US-006: プロフィール編集機能

### User Story
As a 登録済みユーザー
I want to 自分のプロフィール情報を編集できる
So that 最新の情報を他のユーザーに共有できる

### Description
ユーザーが自分のプロフィール情報（名前、自己紹介、プロフィール画像）を
編集・更新できる機能。変更は即座に反映され、他のユーザーから確認できる。

### Acceptance Criteria
- [ ] プロフィールページに「編集」ボタンがある
- [ ] 編集モードでは名前（50文字まで）、自己紹介（500文字まで）を変更できる
- [ ] プロフィール画像はJPG/PNG形式、最大2MBまでアップロード可能
- [ ] 必須項目（名前）が未入力の場合、保存できない
- [ ] 保存成功時は「プロフィールを更新しました」とメッセージ表示
- [ ] キャンセルボタンで変更を破棄して閲覧モードに戻れる
- [ ] 変更内容は保存前にプレビューできる

### Priority
High

### Effort Estimate
5 Story Points

### Status
Approved
```

**良い点:**
- ユーザー視点で書かれている
- 具体的で測定可能な基準
- 優先順位が明確
- 実装規模の見積もりがある
- 依存関係が明示されている

### 悪い要件の例

```markdown
## ❌ 悪い例: プロフィール機能

### User Story
As a ユーザー
I want to プロフィールを使える
So that 良い

### Acceptance Criteria
- [ ] プロフィールがある
- [ ] 編集できる
- [ ] きれいに表示される
```

**問題点:**
- ユーザー役割が曖昧（"ユーザー"は誰?）
- 行動が不明確（"使える"とは具体的に何?）
- 価値が不明（"良い"では何が良いのか不明）
- 受け入れ基準が主観的で測定不可能
- 実装すべき内容が不明確

### 修正版

```markdown
## ✅ 修正版: プロフィール機能

### User Story
As a 登録済みユーザー
I want to 自分のプロフィール情報（名前、自己紹介、画像）を編集・表示できる
So that 他のユーザーに自分の情報を適切に伝えられる

### Description
ユーザーが自身のプロフィール情報を閲覧・編集する機能。
公開情報として他のユーザーからも閲覧可能。

### Acceptance Criteria
- [ ] プロフィールページで現在の情報が表示される
- [ ] 「編集」ボタンクリックで編集モードに切り替わる
- [ ] 名前、自己紹介、プロフィール画像を変更できる
- [ ] 保存後、変更が即座に反映される
- [ ] 他のユーザーから更新後の情報が閲覧できる
- [ ] 変更のキャンセルが可能

### Priority
High

### Status
Draft
```

## 要件の優先順位付け

### MoSCoW法

要件を4つのカテゴリに分類：

```markdown
## Priority Classification

### Must Have (必須)
プロダクトの核となる機能。これがないとリリースできない。

- US-001: ユーザー登録機能
- US-002: ログイン機能
- US-003: 基本的なユーザープロフィール表示

### Should Have (重要)
重要だが、リリースに必須ではない。次の段階で実装すべき。

- US-004: パスワードリセット機能
- US-005: ユーザー検索機能
- US-006: プロフィール編集機能

### Could Have (可能であれば)
あると良いが、優先度は低い。

- US-007: ソーシャルメディア連携
- US-008: テーマカスタマイズ
- US-009: エクスポート機能

### Won't Have (今回は対象外)
今回のスコープには含めない。将来的に検討する可能性がある。

- US-010: モバイルアプリ版
- US-011: AIによる推薦機能
- US-012: 多言語対応
```

### 優先順位マトリクス

価値と複雑さでプロット：

```markdown
## Priority Matrix

### 高価値 × 低複雑さ（最優先）
- US-001: ユーザー登録 [High Priority, 3 SP]
- US-003: ログイン [High Priority, 2 SP]

### 高価値 × 高複雑さ（計画的に実装）
- US-005: 高度な検索機能 [Medium Priority, 8 SP]
- US-006: レポート生成 [Medium Priority, 13 SP]

### 低価値 × 低複雑さ（時間があれば）
- US-008: テーマ切り替え [Low Priority, 2 SP]
- US-009: ショートカットキー [Low Priority, 3 SP]

### 低価値 × 高複雑さ（後回し）
- US-010: カスタムウィジェット [Low Priority, 13 SP]
- US-011: プラグインシステム [Low Priority, 21 SP]
```

### 依存関係の管理

```markdown
## Dependency Graph

### Phase 1: 基盤
US-001: ユーザー登録
  └─> US-002: ログイン
       └─> US-003: プロフィール表示
            ├─> US-004: プロフィール編集
            └─> US-005: ユーザー検索

### Phase 2: 拡張
US-006: パスワードリセット (requires US-001, US-002)
US-007: メール通知 (requires US-001)

### Phase 3: 高度な機能
US-008: ソーシャル連携 (requires US-001, US-003)
US-009: 権限管理 (requires US-001, US-002)
```

## 実践例

### 完全なrequirements.mdの例

```markdown
# Requirements Specification

## Overview
ユーザー管理機能を持つWebアプリケーション。
ユーザーの登録、認証、プロフィール管理、検索機能を提供する。

## User Stories

### US-001: ユーザー登録機能

#### User Story
As a 新規ユーザー
I want to メールアドレスとパスワードで新規アカウントを作成できる
So that アプリケーションのサービスを利用開始できる

#### Description
新規ユーザーがアプリケーションにアカウントを登録する機能。
メールアドレスの検証、パスワード強度チェック、重複チェックを含む。

#### Acceptance Criteria

##### AC-1: 基本的な登録フロー
Given 新規ユーザーが登録ページにアクセスする
When 有効なメールアドレスとパスワードを入力して送信する
Then アカウントが作成される
And 確認メールが送信される
And 確認待ち画面が表示される

##### AC-2: パスワード要件
- [ ] パスワードは8文字以上である
- [ ] 大文字を1文字以上含む
- [ ] 小文字を1文字以上含む
- [ ] 数字を1文字以上含む
- [ ] 特殊文字(@$!%*?&)を1文字以上含む
- [ ] 要件を満たさない場合、リアルタイムでエラー表示

##### AC-3: メールアドレス検証
- [ ] 有効なメールアドレス形式である
- [ ] 既に登録済みの場合、"このメールアドレスは既に使用されています"と表示
- [ ] 確認メール内のリンクをクリックするとアカウントが有効化される
- [ ] 確認メールは24時間有効

##### AC-4: エラーハンドリング
- [ ] ネットワークエラー時は適切なメッセージを表示
- [ ] サーバーエラー時は"現在登録できません。しばらくしてから再試行してください"と表示
- [ ] フォーム送信中はボタンを無効化し、ローディング表示

#### Priority
Must Have

#### Effort Estimate
5 Story Points

#### Status
Approved

#### Dependencies
None

#### Related
- Design: [design.md#authentication-system](../design.md#authentication-system)
- Tasks: [tasks.md#task-001](../tasks.md#task-001)
- Tech Stack: [steering/tech.md#authentication](../../steering/tech.md#authentication)

---

### US-002: ログイン機能

#### User Story
As a 登録済みユーザー
I want to メールアドレスとパスワードでログインできる
So that 自分のアカウントにセキュアにアクセスできる

#### Description
登録済みユーザーがアプリケーションにログインする機能。
セッション管理、アカウントロック、Remember Me機能を含む。

#### Acceptance Criteria

##### AC-1: 正常なログイン
Given 有効なアカウントを持つユーザー
When 正しいメールアドレスとパスワードを入力する
Then ダッシュボードにリダイレクトされる
And セッションが作成される（有効期限: 24時間）
And "ログインしました"とメッセージ表示

##### AC-2: 無効な認証情報
Given ユーザーがログインページにいる
When 誤ったメールアドレスまたはパスワードを入力する
Then "メールアドレスまたはパスワードが正しくありません"と表示
And ログイン試行回数がカウントされる
And パスワード欄のみクリアされる（メールアドレスは保持）

##### AC-3: アカウントロック
- [ ] 5回連続でログイン失敗するとアカウントがロックされる
- [ ] ロック時は"アカウントがロックされました。15分後に再試行してください"と表示
- [ ] 15分後に自動的にロックが解除される
- [ ] 管理者による手動ロック解除も可能

##### AC-4: Remember Me機能
- [ ] "ログイン状態を保持"チェックボックスがある
- [ ] チェック時、セッション有効期限が30日間になる
- [ ] 次回訪問時、自動的にログイン状態になる
- [ ] セキュアなトークンを使用（LocalStorage保存）

##### AC-5: パフォーマンス
- [ ] ログイン処理は2秒以内に完了する
- [ ] 認証情報の検証は1秒以内に完了する

Must Have

#### Dependencies

### US-003: ユーザー検索機能

#### User Story
As a 管理者
I want to 名前やメールアドレスでユーザーを検索できる
So that 特定のユーザーを素早く見つけて管理できる

#### Description
管理者がユーザーリストから特定のユーザーを検索する機能。
リアルタイム検索、複数条件、検索履歴をサポート。

#### Acceptance Criteria

##### AC-1: 基本検索
- [ ] 検索バーに文字を入力するとリアルタイムで絞り込まれる
- [ ] 名前、メールアドレス、ユーザーIDで検索可能
- [ ] 部分一致検索をサポート（大文字小文字区別なし）
- [ ] 検索結果は0.5秒以内に表示される

##### AC-2: 検索結果表示
- [ ] 検索結果には名前、メールアドレス、登録日を表示
- [ ] 結果は名前の昇順でソート（変更可能）
- [ ] ページネーション（1ページ20件）
- [ ] 結果が0件の場合、"該当するユーザーが見つかりませんでした"と表示

##### AC-3: 高度な検索
- [ ] 登録日範囲での絞り込み
- [ ] アカウントステータス（有効/無効）での絞り込み
- [ ] 複数条件の組み合わせ検索
- [ ] 検索条件のクリアボタン

##### AC-4: 検索履歴
- [ ] 直近10件の検索クエリを保存
- [ ] 履歴からワンクリックで再検索
- [ ] 履歴のクリア機能

##### AC-5: パフォーマンス
- [ ] 10,000ユーザーでもスムーズに動作
- [ ] インデックスによる最適化
- [ ] 検索結果のキャッシュ（5分間）

#### Priority
Should Have

#### Effort Estimate
8 Story Points

#### Status
In Progress

#### Dependencies
- US-001 (ユーザーデータが存在する必要がある)
- US-002 (管理者としてログインする必要がある)

#### Technical Notes
- Elasticsearchまたは同等の検索エンジンの使用を検討
- データベースにフルテキストインデックスを作成
- 検索クエリのサニタイゼーションを実装

#### Related
- Design: [design.md#search-architecture](../design.md#search-architecture)
- Tasks: [tasks.md#task-005](../tasks.md#task-005)
