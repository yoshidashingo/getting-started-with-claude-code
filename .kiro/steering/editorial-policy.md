# 編集方針・ポリシー

**編集長**: 技術書籍制作歴20年のベテラン編集長

このドキュメントは、Claude Code初心者ガイドの全ドキュメントに適用される編集基準を定めます。すべての執筆者・編集者は、この方針に従って高品質な技術ドキュメントを維持する責任があります。

---

## 基本原則

### 1. 読者ファースト
- **読者は初心者である**: 専門用語は必ず説明する
- **読者の時間は貴重**: 冗長な表現を排除し、簡潔に
- **読者は実践したい**: すべての例は実行可能であること

### 2. 正確性の徹底
- **技術情報は最新**: 2024-2025年の最新情報を反映
- **検証済みの内容のみ**: すべてのコード例、コマンドは動作確認済み
- **曖昧な表現を排除**: 「たぶん」「おそらく」「〜かもしれない」は使用禁止

### 3. 一貫性の維持
- **用語の統一**: プロジェクト全体で同じ用語を使用
- **フォーマットの統一**: 見出し、コードブロック、リストの書式を統一
- **トーンの統一**: 文体、敬体・常体の一貫性

## 文章品質基準

### A. 明瞭性
❌ **悪い例**:
```
Claude Codeは便利なツールで、いろいろなことができます。
```

✅ **良い例**:
```
Claude Codeは自然言語でのコード生成、既存コードの編集、デバッグ支援を提供するAI開発ツールです。
```

**基準**:
- 主語・述語を明確に
- 一文は60文字以内を推奨
- 抽象的な表現を避け、具体的に

### B. 簡潔性
❌ **悪い例**:
```
このセクションでは、Claude Codeの様々な機能について、一つ一つ詳しく説明していきたいと思います。
```

✅ **良い例**:
```
このセクションでは、Claude Codeの全機能を詳しく説明します。
```

**基準**:
- 冗長な接続詞を削除（「〜について」「〜に関して」の乱用禁止）
- 意味のない前置きを削除
- 同じ内容の繰り返しを避ける

### C. 論理性
❌ **悪い例**:
```
MCPサーバーは便利です。GitHubと連携できます。Sentryも使えます。
```

✅ **良い例**:
```
MCPサーバーを使うと、GitHub、Sentry、PostgreSQLなどの外部サービスと統合できます。これにより、Issue管理やエラー監視を自動化できます。
```

**基準**:
- 因果関係を明確に
- 段落間の論理的つながりを維持
- 結論を先に、詳細を後に（PREP法）

## 技術内容の品質基準

### 1. コード例
**必須要件**:
- ✅ シンタックスハイライト付きコードブロック使用
- ✅ 言語指定（```javascript, ```bash など）
- ✅ 実行可能で動作確認済み
- ✅ コメントで重要部分を説明
- ✅ エラーハンドリングを含む

❌ **禁止事項**:
- インラインコードでの長いコード例
- 未検証のコード
- エラーの出るコード
- 説明なしの複雑なコード

### 2. コマンド例
**必須要件**:
- ✅ プロンプト記号（`$`, `>` など）を明記
- ✅ 実行結果の例を含める（必要に応じて）
- ✅ 前提条件を明記（ディレクトリ、権限など）
- ✅ エラー時の対処法を記載

**フォーマット**:
```bash
# コメントで目的を説明
$ command --option argument
```

### 3. 専門用語
**ルール**:
1. **初出時に必ず説明**: 「MCP（Model Context Protocol）」
2. **略語の乱用禁止**: 2回目以降も文脈によってフル名を使用
3. **日本語訳を提供**: 「Hooks（フック）」
4. **用語集へのリンク**: INDEX.mdに登録

## 構造と体裁の基準

### 1. 見出し構造
**ルール**:
- H1（`#`）: ドキュメントタイトルのみ、1つだけ
- H2（`##`）: 主要セクション
- H3（`###`）: サブセクション
- H4以下（`####`）: 必要最小限に
- **見出しの階層を飛ばさない**: H2の次にH4は禁止

### 2. リスト
**ルール**:
- 箇条書きは3〜7項目が理想
- 並列関係にあるものをリストに
- リスト項目の文末を統一（「。」ありなし）
- ネストは2階層まで

### 3. 表（テーブル）
**ルール**:
- 見出し行を必ず設定
- セル内の改行禁止（複数行は別セルに）
- 3列以上、10行以内が理想
- モバイル表示を考慮（横幅注意）

### 4. 強調
**使い分け**:
- **太字（`**`）**: 重要な用語、強調
- *イタリック（`*`）*: 軽い強調（日本語では使用頻度低）
- `コード（ `` `）`: ファイル名、コマンド、変数名、コード片

**禁止事項**:
- ❌ 全文太字
- ❌ 複数の強調の重複（`***`）
- ❌ 安易な強調の乱用

## リンクとクロスリファレンス

### 1. 内部リンク
**ルール**:
- 相対パスを使用: `[リンク](../path/to/file.md)`
- リンクテキストは明確に: ❌「こちら」「ここ」 ✅「MCP基礎ドキュメント」
- リンク切れゼロ: すべてのリンクを定期チェック

### 2. 外部リンク
**ルール**:
- 公式ドキュメント優先
- URLは短縮せず完全なURLを使用
- リンク先の信頼性を確認
- 可能な限りHTTPS

### 3. クロスリファレンス
**必須**:
- 関連ドキュメントへのリンクを各ドキュメント末尾に配置
- 前提知識のドキュメントへのリンク
- 次のステップへのリンク

## 日本語表記ルール

### 1. 敬体・常体
**基準**: **常体（である調）で統一**

❌ 敬体混在:
```
Claude Codeを使います。これは便利である。
```

✅ 常体統一:
```
Claude Codeを使う。これは便利である。
```

### 2. 句読点
- 読点（、）: 文の区切り、意味の切れ目
- 句点（。）: 文末
- コロン（:）: リストの前、説明の前
- 中点（・）: 並列項目（「JavaScript・Python・React」）

### 3. カタカナ表記
**長音符号の使用**:
- ✅ サーバー、ユーザー、エラー（長音符号あり）
- ❌ サーバ、ユーザ、エラ（長音符号なし）

**例外**: コンピュータ（長音符号なし）が一般的

### 4. 数字・アルファベット
- 半角を使用: ✅ 1, 2, 3, A, B, C
- 全角は不可: ❌ １、２、３、Ａ、Ｂ、Ｃ

## 禁止表現リスト

### 1. 曖昧な表現
- ❌ 「いくつかの方法」→ ✅ 「3つの方法」
- ❌ 「様々な機能」→ ✅ 「12の機能」
- ❌ 「簡単に」→ ✅ 「3ステップで」
- ❌ 「高度な」→ ✅ 「TypeScript型定義を使った」

### 2. 口語的表現
- ❌ 「〜してみましょう」→ ✅ 「〜する」
- ❌ 「〜だったりします」→ ✅ 「〜である」
- ❌ 「〜みたいな」→ ✅ 「〜のような」
- ❌ 「結構」「かなり」「割と」→ 削除または具体的に

### 3. 冗長な表現
- ❌ 「〜することができます」→ ✅ 「〜できる」
- ❌ 「〜という形になります」→ ✅ 「〜である」
- ❌ 「基本的に」→ 削除
- ❌ 「〜に関して」「〜について」→ 削除または簡潔に

## 編集プロセス

### 1. ドラフト作成
- 構造を先に決定
- 見出しとサブ見出しを作成
- 各セクションの概要を記載

### 2. 内容執筆
- 実践例から書き始める
- コード例を先に作成・検証
- 説明は後から追加

### 3. 自己レビュー
- 24時間寝かせる
- 品質チェックリストで確認
- 声に出して読み、リズムを確認

### 4. 編集長レビュー（自動）
- Hookによる自動チェック
- 編集方針違反の検出
- 改善提案の取得

### 5. 最終確認
- リンク切れチェック
- 用語の一貫性確認
- 全体の整合性確認
